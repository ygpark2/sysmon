AWS 플랫폼 대응 아키텍처

AOBS Stack / Docker Swarm 기반 관측 시스템 설계 문서
문서 목적
이 문서는 현재 프로젝트가 생성하는 Docker Swarm 서버 스택과 클라이언트 스택을 AWS 환경에 배치할 때 대응되는 구성, 데이터 흐름, 네트워크 경계, 저장소 및 운영 고려사항을 설명합니다.

1. 결론 요약

이 프로젝트는 make stack과 make client-stack으로 Docker Compose v3.8 형식의 Swarm stack 파일을 생성합니다. 따라서 가장 직접적인 AWS 배치 모델은 EC2 기반 Docker Swarm 클러스터입니다.

외부 사용자는 ALB를 통해 HAProxy로 접근하고, HAProxy는 Grafana로 요청을 전달합니다. 애플리케이션의 logs, metrics, traces는 클라이언트의 Alloy 또는 OTel Collector를 거쳐 중앙 OTel Collector로 들어옵니다. 로그는 OpenSearch 또는 선택적 Loki로, 메트릭은 Prometheus로 저장하며 Grafana가 이를 조회합니다.

현재 저장소에는 Terraform, CloudFormation, CDK 또는 AWS SDK 코드가 없습니다. 아래 AWS 리소스는 이 프로젝트를 AWS에 배치하기 위한 참조 설계이며, 실제 생성과 권한 설정은 별도의 IaC/운영 코드가 필요합니다.

3. 네트워크 구성

3.1 VPC와 Subnet

  • 최소 2개 Availability Zone에 Public Subnet과 Private Subnet을 구성합니다.
  • Public Subnet에는 ALB와 NAT Gateway를 배치합니다.
  • Swarm manager, observability worker, application worker는 Private Subnet에 배치합니다.
  • 관리 접속은 SSH를 인터넷에 노출하기보다 Systems Manager Session Manager를 우선 고려합니다.

3.2 Security Group 권장 규칙

출발지목적지 / 포트용도

Prometheus SGnode-exporter :9100, OTel :8889메트릭 scrape
수집기/로그 에이전트 SGOpenSearch :9200, Loki :3100로그 전송

실제 포트와 source CIDR은 운영 환경의 네트워크 정책에 맞춰 최소 권한으로 제한해야 합니다. OpenSearch와 Loki를 인터넷에 직접 노출하지 않는 것이 원칙입니다.

4. 데이터 흐름

4.1 애플리케이션 텔레메트리

  1. 애플리케이션이 OTLP logs, metrics, traces를 Alloy 또는 client OTel Collector에 전송합니다.
  2. Alloy와 client OTel Collector는 CLIENT_OTLP_ENDPOINT 기본값인 http://otel-collector:4318을 사용합니다.
  3. 중앙 OTel Collector는 memory limiter와 batch processor를 적용합니다.
  4. logs는 OpenSearch exporter 또는 Loki exporter로 보냅니다.
  5. metrics는 OTel Collector의 Prometheus endpoint :8889로 노출하고 Prometheus가 scrape합니다.

4.2 호스트 로그

Fluent Bit, Filebeat, Vector는 클라이언트 EC2의 /var/log/*.log를 읽습니다. 현재 템플릿 기준 이 세 에이전트는 OpenSearch endpoint로 직접 전송합니다. 따라서 Loki-only 구성에서는 Alloy 또는 OTel client collector 중심으로 운영하는 편이 적합합니다.

4.3 조회 경로

운영자는 ALB를 통해 HAProxy에 접속하고, HAProxy가 Grafana :3000으로 라우팅합니다. Grafana에는 Prometheus, OpenSearch, 선택적 Loki datasource가 provisioning됩니다. metrics dashboard는 Prometheus를, logs dashboard는 OpenSearch 또는 Loki를 조회합니다.

5. 저장소 및 장애 대응

  • OpenSearch: 노드별 EBS를 사용하고, 다중 노드 구성에서는 AZ를 분산합니다. 백업을 위해 별도 snapshot 정책을 추가해야 합니다.
  • Prometheus: 로컬 TSDB는 EBS에 저장됩니다. 장기 보관이 필요하면 remote_write 대상 또는 Amazon Managed Service for Prometheus로의 확장을 검토합니다.
  • Grafana: dashboard provisioning 파일은 코드로 재생성되지만, 사용자 설정과 plugin 상태는 ./data/grafana에 보존됩니다.
  • Loki: 선택 서비스이며 ENABLE_LOKI=true일 때만 활성화됩니다.
  • EBS 장애: 단일 EC2에만 연결되는 volume은 해당 노드 장애 시 복구 절차가 필요합니다. OpenSearch 데이터는 multi-AZ node와 snapshot을 함께 구성해야 합니다.

6. 배포 순서

1. AWS VPC, Subnet, Route Table, SG, EC2 Swarm cluster 준비
2. EBS volume mount 및 Docker Swarm 초기화
3. 관리용 환경 파일(.env)과 비밀번호 Secret 준비
4. make stack ENABLE_OPENSEARCH=true ENABLE_OTEL=true ...
5. make deploy
6. make client-stack ENABLE_CLIENT_ALLOY=true ENABLE_CLIENT_NODE_EXPORTER=true ...
7. docker stack deploy -c deploy/stack.client.yml ovs-client
8. ALB target health, Grafana datasource, Prometheus targets, OpenSearch index 확인

운영 배포에서는 비밀번호를 일반 파일이나 명령행에 남기지 말고 AWS Secrets Manager 또는 SSM Parameter Store와 CI/CD secret 연계를 사용하는 것을 권장합니다.

다이어그램 읽는 순서

  1. 사용자 요청은 Internet Gateway와 ALB를 거쳐 HAProxy로 들어옵니다.
  2. HAProxy는 프로젝트의 기존 설정처럼 Grafana :3000으로 요청을 전달합니다.
  3. 애플리케이션 텔레메트리는 client stack의 Alloy 또는 OTel client collector에서 중앙 OTel Collector로 전송됩니다.
  4. 중앙 collector는 로그를 OpenSearch/Loki로, 메트릭을 Prometheus scrape endpoint로 노출합니다.
  5. Grafana는 Prometheus와 로그 저장소를 조회하며, 데이터 서비스는 EBS에 영속화됩니다.
